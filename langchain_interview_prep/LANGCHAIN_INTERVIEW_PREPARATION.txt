--------------------------------------------------------------------------------
 1. What is LangChain?
--------------------------------------------------------------------------------
QUESTION: What is LangChain?

SIMPLE ANSWER:
A framework for building LLM applications. It gives you uniform components -
models, prompts, parsers, tools, retrievers, agents - and lets you compose them
into chains (LCEL) and graphs. It wraps many providers (Gemini, OpenAI, ...)
behind one interface.

EXAMPLE FROM OUR CODE:
ChatGoogleGenerativeAI is one model behind the same interface that OpenAI and
Anthropic also use (01_basic_model/main.py). Components compose with `|` (07_lcel).

--------------------------------------------------------------------------------
 2. Why LangChain?
--------------------------------------------------------------------------------
QUESTION: Why use LangChain instead of calling the Gemini SDK directly?

SIMPLE ANSWER:
Three reasons. 1) Provider-agnostic interface - switch models without rewriting
code. 2) Composability - prompts, parsers, tools, and agents combine with `|`.
3) Ecosystem - loaders, vector stores, RAG, agents, LangGraph, middleware are
ready-made instead of hand-built.

EXAMPLE FROM OUR CODE:
The same prompt|model|parser chain works no matter which ChatModel you use
(07_lcel/main.py). RAG takes 8 lines with TextLoader + FAISS + retriever
(15_basic_rag/main.py).

--------------------------------------------------------------------------------
 3. Model
--------------------------------------------------------------------------------
QUESTION: How do you call a chat model in LangChain?

SIMPLE ANSWER:
Create a ChatModel (e.g. ChatGoogleGenerativeAI), then call invoke(). It returns
an AIMessage; the text is in .content. Every model supports invoke, batch, stream
(and async versions).

EXAMPLE FROM OUR CODE:
model = ChatGoogleGenerativeAI(model="gemini-3.5-flash", api_key=key)
response = model.invoke("hello")   # response.content = the answer
(01_basic_model/main.py)

--------------------------------------------------------------------------------
 4. Messages
--------------------------------------------------------------------------------
QUESTION: How does LangChain represent a conversation?

SIMPLE ANSWER:
As a list of message objects, each with a role: SystemMessage (behaviour),
HumanMessage (user), AIMessage (model), and ToolMessage (tool results). You pass
the whole list to the model; order = conversation order.

EXAMPLE FROM OUR CODE:
messages = [SystemMessage(...), HumanMessage(...)]
response = model.invoke(messages)         # an AIMessage
(02_messages/main.py)

--------------------------------------------------------------------------------
 5. Prompt templates
--------------------------------------------------------------------------------
QUESTION: What is a prompt template and why use one?

SIMPLE ANSWER:
A reusable prompt with {variables}. ChatPromptTemplate.from_messages([...]) builds
it; prompt.invoke({"x": ...}) fills variables and returns messages. It replaces
manual string concatenation.

EXAMPLE FROM OUR CODE:
prompt = ChatPromptTemplate.from_messages([("human", "What is {topic}?")])
messages = prompt.invoke({"topic": "RAG"})
(03_prompt_template/main.py)

--------------------------------------------------------------------------------
 6. Structured output
--------------------------------------------------------------------------------
QUESTION: How do you get structured output from a model?

SIMPLE ANSWER:
Define a Pydantic class, then model.with_structured_output(Schema). invoke()
returns a validated instance of that class instead of free text. For agents, pass
response_format=Schema to create_agent.

EXAMPLE FROM OUR CODE:
class Person(BaseModel): name: str; age: int
person = model.with_structured_output(Person).invoke("Alice is 30.")
(04_structured_output/main.py, 20_structured_agent/main.py)

--------------------------------------------------------------------------------
 7. Runnable
--------------------------------------------------------------------------------
QUESTION: What is a Runnable in LangChain?

SIMPLE ANSWER:
The universal interface of every callable component: models, prompts, parsers,
chains, tools, agents. They all support invoke, batch, stream, and their async
a-variants. RunnableLambda wraps a plain function into a Runnable.

EXAMPLE FROM OUR CODE:
runnable = RunnableLambda(double)
runnable.invoke(4); runnable.batch([1,2,3]); runnable.stream(4)
(06_runnable/main.py)

--------------------------------------------------------------------------------
 8. LCEL
--------------------------------------------------------------------------------
QUESTION: What is LCEL and how does the pipe operator work?

SIMPLE ANSWER:
LangChain Expression Language: composing Runnables with `|`. The output of the
left runnable becomes the input of the right one. chain = prompt | model | parser.
The result is still a Runnable.

EXAMPLE FROM OUR CODE:
chain = prompt | model | parser
result = chain.invoke({"topic": "LCEL"})
(07_lcel/main.py)

--------------------------------------------------------------------------------
 9. Chain
--------------------------------------------------------------------------------
QUESTION: What is a chain?

SIMPLE ANSWER:
A fixed pipeline of Runnables. No decisions - data flows prompt -> model -> parser
every time. Different from an agent, which decides its own steps.

EXAMPLE FROM OUR CODE:
chain = prompt | model | StrOutputParser()     # translate example
(05_basic_chain/main.py)

--------------------------------------------------------------------------------
 10. Tool
--------------------------------------------------------------------------------
QUESTION: How do you create a tool?

SIMPLE ANSWER:
Put @tool on a function. The docstring becomes the description, type hints become
the JSON argument schema. The tool has .name, .description, .args_schema, .invoke.

EXAMPLE FROM OUR CODE:
@tool
def add_numbers(a: int, b: int) -> int:
    """Add two numbers together."""
    return a + b
(17_tools/main.py)

--------------------------------------------------------------------------------
 11. Tool calling
--------------------------------------------------------------------------------
QUESTION: How does tool calling work?

SIMPLE ANSWER:
The model is given the tools' JSON schemas (bind_tools). It replies with an
AIMessage that has tool_calls - what it WANTS to call - but the model does NOT
execute. Your code (or an agent) runs the function and feeds the ToolMessage back.

EXAMPLE FROM OUR CODE:
response = model.bind_tools([add_numbers]).invoke("What is 12 + 30?")
response.tool_calls   # [{'name': 'add_numbers', 'args': {...}}]
(17_tools/main.py)

--------------------------------------------------------------------------------
 12. Agent
--------------------------------------------------------------------------------
QUESTION: What is an agent?

SIMPLE ANSWER:
An LLM-driven loop. The model reads the state, decides the next step (answer
directly or call a tool), sees tool results, and repeats until done. The LLM
decides the path; a chain has a fixed path.

EXAMPLE FROM OUR CODE:
agent = create_agent(model=model, tools=[add_numbers, get_weather], system_prompt="...")
result = agent.invoke({"messages": [{"role": "user", "content": "What is 5 + 7?"}]})
answer = result["messages"][-1].content
(18_basic_agent/main.py)

--------------------------------------------------------------------------------
 13. create_agent
--------------------------------------------------------------------------------
QUESTION: What is create_agent and how does it relate to LangGraph?

SIMPLE ANSWER:
The current high-level agent API in LangChain. It takes a model, tools, a system
prompt, and options (checkpointer, middleware, response_format, interrupt_before)
and returns a compiled LangGraph that runs the agent loop (model -> tools ->
model ...). You get the agent without building the graph by hand.

EXAMPLE FROM OUR CODE:
agent = create_agent(model=model, tools=[...], checkpointer=InMemorySaver())
(18_basic_agent/main.py, 21_memory/main.py)
The graph it builds looks like 30_langchain_langgraph/main.py.

--------------------------------------------------------------------------------
 14. ReAct
--------------------------------------------------------------------------------
QUESTION: What is ReAct?

SIMPLE ANSWER:
Reason + Act. The agent loop: think about what to do, emit a tool call (Act), get
the result (Observe), think again. The loop ends when the model answers without a
tool call. create_agent produces this loop.

EXAMPLE FROM OUR CODE:
The two-step multiply example where printing all messages shows
AIMessage(tool_calls) -> ToolMessage -> AIMessage(answer)
(19_react_agent/main.py)

--------------------------------------------------------------------------------
 15. Memory
--------------------------------------------------------------------------------
QUESTION: How does an agent remember a conversation?

SIMPLE ANSWER:
With a checkpointer plus a thread_id. The checkpointer saves state after every
run; the same thread_id resumes that conversation, so history is in the model's
context. Long-term memory across threads uses a store - a bigger system.

EXAMPLE FROM OUR CODE:
agent = create_agent(..., checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "conversation-1"}}
agent.invoke({"messages": [...]}, config=config)
(21_memory/main.py)

--------------------------------------------------------------------------------
 16. Middleware
--------------------------------------------------------------------------------
QUESTION: What is middleware in LangChain agents?

SIMPLE ANSWER:
Reusable hooks that wrap agent steps: before_model, after_model, wrap_model_call,
wrap_tool_call. Used for logging, retries, PII redaction, guardrails. Subclass
AgentMiddleware and pass instances to create_agent(middleware=[...]).

EXAMPLE FROM OUR CODE:
class LoggingMiddleware(AgentMiddleware):
    def before_model(self, state, runtime): print(state["messages"][-1].content); return None
agent = create_agent(..., middleware=[LoggingMiddleware()])
(22_middleware/main.py)

--------------------------------------------------------------------------------
 17. Streaming
--------------------------------------------------------------------------------
QUESTION: invoke vs stream?

SIMPLE ANSWER:
invoke() waits and returns the whole answer. stream() yields chunks as the model
produces them. Streaming improves perceived latency. Agents can stream too
(agent.stream yields state after each step).

EXAMPLE FROM OUR CODE:
for chunk in model.stream("...") : print(chunk.content, end="", flush=True)
for step in agent.stream({"messages": [...]}): print(step)
(24_streaming/main.py)

--------------------------------------------------------------------------------
 18. RAG
--------------------------------------------------------------------------------
QUESTION: What is RAG and how do you build it?

SIMPLE ANSWER:
Retrieval-Augmented Generation: ground the LLM in your documents. Indexing =
load -> split -> embed -> store. Querying = retrieve relevant chunks -> put them
in the prompt as context -> model answers from that context only.

EXAMPLE FROM OUR CODE:
doc = TextLoader("data/company.txt").load()[0]
chunks = RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=50).split_documents([doc])
store = FAISS.from_documents(chunks, embeddings)
chain = get_context | prompt | model | StrOutputParser()
(15_basic_rag/main.py)

--------------------------------------------------------------------------------
 19. Embeddings
--------------------------------------------------------------------------------
QUESTION: What is an embedding?

SIMPLE ANSWER:
A vector (list of floats) that represents the meaning of a text. Similar texts
produce similar vectors. Embeddings enable similarity search. The same embedding
model must be used for indexing and querying.

EXAMPLE FROM OUR CODE:
embeddings = GoogleGenerativeAIEmbeddings(model="models/text-embedding-004", api_key=key)
vector = embeddings.embed_query("LangChain is a framework...")   # len(vector)
(12_embeddings/main.py)

--------------------------------------------------------------------------------
 20. Vector store
--------------------------------------------------------------------------------
QUESTION: What does a vector store do?

SIMPLE ANSWER:
Stores documents as embedding vectors and returns the closest ones to a query via
similarity search. add_documents adds; similarity_search(query, k=n) finds the n
nearest. FAISS and Chroma are local; Pinecone is hosted - same interface.

EXAMPLE FROM OUR CODE:
vector_store = FAISS.from_documents(docs, embeddings)
vector_store.add_documents(more_docs)
results = vector_store.similarity_search("query", k=2)
(13_vector_store/main.py)

--------------------------------------------------------------------------------
 21. Retriever
--------------------------------------------------------------------------------
QUESTION: Vector store vs retriever?

SIMPLE ANSWER:
The vector store is storage + vector search. The retriever is the interface that
returns relevant documents for a query - any backend (vector, keyword, hybrid)
can power it. RAG code talks to the retriever, so backends are swappable.

EXAMPLE FROM OUR CODE:
retriever = vector_store.as_retriever(search_kwargs={"k": 2})
results = retriever.invoke("Which framework helps build LLM apps?")
(14_retriever/main.py)

--------------------------------------------------------------------------------
 22. Agentic RAG
--------------------------------------------------------------------------------
QUESTION: Normal RAG vs agentic RAG?

SIMPLE ANSWER:
Normal RAG always retrieves. Agentic RAG gives the retrieval to an agent as a
tool, so it decides WHEN to retrieve, can refine the query, or combine retrieval
with other tools (SQL, web).

EXAMPLE FROM OUR CODE:
@tool
def search_products(query: str) -> str:
    return "\n".join(d.page_content for d in vector_store.similarity_search(query, k=2))
agent = create_agent(model=model, tools=[search_products], system_prompt="...")
(27_rag_agent/main.py)

--------------------------------------------------------------------------------
 23. SQL agent
--------------------------------------------------------------------------------
QUESTION: How does an SQL agent work?

SIMPLE ANSWER:
The LLM turns a natural-language question into SQL, a tool executes it, and the
agent summarizes the rows. Safety: expose a read-only tool (SELECT only) so the
model cannot damage data.

EXAMPLE FROM OUR CODE:
@tool
def run_sql_query(query: str) -> str:
    if not query.strip().lower().startswith("select"): return "Only SELECT allowed."
    return "\n".join(str(r) for r in DB.execute(query).fetchall())
agent = create_agent(model=model, tools=[run_sql_query], system_prompt="...")
(26_sql_agent/main.py)

--------------------------------------------------------------------------------
 24. Multi-agent
--------------------------------------------------------------------------------
QUESTION: What is a multi-agent system?

SIMPLE ANSWER:
Several agents with different roles that collaborate. A supervisor routes a
request to the right specialist. Each agent is its own system prompt + model;
they communicate through inputs and outputs (or shared graph state).

EXAMPLE FROM OUR CODE:
supervisor(question) decides RESEARCH vs WRITE, then calls
research_agent(question) and/or writer_agent(facts).
(29_multi_agent/main.py)

--------------------------------------------------------------------------------
 25. LangChain vs LangGraph
--------------------------------------------------------------------------------
QUESTION: LangChain vs LangGraph?

SIMPLE ANSWER:
LangChain = components and high-level APIs (models, prompts, tools, chains,
create_agent). LangGraph = low-level orchestration: State, Nodes, edges, routing,
loops, checkpoints. LangChain agents RUN on LangGraph underneath. Use LangChain
for most apps; LangGraph when you need custom control flow.

EXAMPLE FROM OUR CODE:
30_langchain_langgraph/main.py puts a LangChain model and tool inside a
StateGraph with a conditional loop - the same graph create_agent builds.

--------------------------------------------------------------------------------
 26. LangChain vs LlamaIndex
--------------------------------------------------------------------------------
QUESTION: LangChain vs LlamaIndex?

SIMPLE ANSWER:
LangChain is a general LLM-app framework: chains, tools, agents, integrations.
LlamaIndex specializes in data + RAG: data connectors, indexing, query engines.
For agent-heavy apps use LangChain; for pure document RAG LlamaIndex is simpler.

EXAMPLE FROM OUR CODE:
LangChain's RAG is generic enough to add tools and agents on top
(15_basic_rag -> 27_rag_agent progression).

--------------------------------------------------------------------------------
 27. LangChain vs CrewAI
--------------------------------------------------------------------------------
QUESTION: LangChain vs CrewAI?

SIMPLE ANSWER:
CrewAI is a thin framework focused on role-based multi-agent collaboration
(agents, tasks, crews). LangChain is the broader platform; it can build the same
thing with more control (supervisor routing, LangGraph). CrewAI gives less code
for multi-agent, LangChain more power and flexibility.

EXAMPLE FROM OUR CODE:
LangChain multi-agent by hand: supervisor function + specialist functions
(29_multi_agent/main.py) - CrewAI would wrap similar roles in classes.

 PART 2 - COMPARISONS YOU MUST BE ABLE TO EXPLAIN
================================================================================

--------------------------------------------------------------------------------
 LLM CALL vs CHAIN vs WORKFLOW vs AGENT
--------------------------------------------------------------------------------
LLM CALL  : model.invoke(text) -> one answer. No structure around it.
CHAIN     : fixed pipeline of Runnables (prompt | model | parser). Same path
            every run.  -> 05_basic_chain
WORKFLOW  : predetermined sequence of steps, possibly with branching/parallelism
            (RunnableBranch, RunnableParallel, LangGraph graph with fixed edges).
            The CODE decides the path.  -> 08_parallel, 09_branching, 30
AGENT     : the LLM decides the path at runtime (loop + tools + tool results).
            -> 18_basic_agent
Rule of thumb: fixed path = chain/workflow. Dynamic path decided by the model
while running = agent.

--------------------------------------------------------------------------------
 BASIC AGENT vs REACT vs AUTONOMOUS AGENT
--------------------------------------------------------------------------------
BASIC AGENT   : an agent with a few tools and a prompt; loop of model/tool until
                done.  -> 18_basic_agent
REACT         : the pattern inside it: Reason -> Act -> Observe -> repeat.
                -> 19_react_agent
AUTONOMOUS    : ReAct at scale - long-horizon tasks, many tools, persistence,
                planning, self-correction. Same idea, more robustness.
Answer "they are the same loop with increasing capability/autonomy."

--------------------------------------------------------------------------------
 LANGCHAIN vs LANGGRAPH
--------------------------------------------------------------------------------
LANGCHAIN : components + high-level APIs (create_agent gives you an agent fast).
LANGGRAPH : you build the graph (State, Nodes, edges) for full control.
Both in one stack: LangChain components inside LangGraph nodes. Use LangGraph
directly when you need custom loops, checkpoints, or human-in-the-loop that the
high-level API can't express.

--------------------------------------------------------------------------------
 VECTOR STORE vs RETRIEVER
--------------------------------------------------------------------------------
VECTOR STORE : storage + similarity search (FAISS, Chroma, Pinecone).
RETRIEVER    : interface that returns documents for a query; the vector store is
               just one implementation (keyword/hybrid are others).
Talk to the retriever in your code -> backends are swappable.

--------------------------------------------------------------------------------
 RAG vs AGENTIC RAG
--------------------------------------------------------------------------------
RAG         : always retrieve, then generate.  -> 15_basic_rag
AGENTIC RAG : an agent decides whether/when to retrieve, can refine queries and
              use other tools.  -> 27_rag_agent
Difference = who decides retrieval: the pipeline (fixed) or the model (dynamic).

--------------------------------------------------------------------------------
 STATE vs MEMORY
--------------------------------------------------------------------------------
STATE   : all data flowing through a graph at a given time (messages, counters,
          user_id). Defined by a schema; nodes read and update it.  -> 30
MEMORY  : the part of state that PERSISTS across runs (usually messages), so the
          agent remembers a conversation.  -> 21_memory
State = current data; memory = durable state keyed by thread_id.

--------------------------------------------------------------------------------
    class State(TypedDict):
        messages: Annotated[list[AnyMessage], add_messages]

    def call_model(state): return {"messages": [model.invoke(state["messages"])]}

    def should_continue(state):
        return "tools" if state["messages"][-1].tool_calls else END

    g = StateGraph(State)
    g.add_node("model", call_model); g.add_node("tools", ToolNode([add_numbers]))
    g.add_edge(START, "model"); g.add_conditional_edges("model", should_continue)
    g.add_edge("tools", "model")
    app = g.compile()
