1. OS BASICS
================================================================================

CONCEPT:
An Operating System is system software that manages computer hardware and
software resources and provides services for computer programs. It acts as
both a resource manager and an abstraction layer between the user and hardware.

SIMPLE EXPLANATION:
Think of an OS as a government: it allocates resources (CPU time, memory,
devices) to processes, enforces rules (security, access control), and hides
the complexity of hardware so applications don't need to deal with raw
electronics.

INTERVIEW ANSWER:
"An OS has two key roles. First, it's a resource manager — it allocates CPU,
memory, I/O devices, and file storage among competing processes fairly and
efficiently. Second, it's an abstraction layer — it hides hardware complexity
behind clean APIs so programmers interact with logical concepts like files
and processes instead of disk sectors and registers."

MAIN RESPONSIBILITIES:
• Process Management: creation, scheduling, termination, IPC, synchronization
• Memory Management: allocation, deallocation, virtual memory, paging
• File Management: storage, retrieval, naming, protection, directory structure
• I/O Management: device drivers, buffering, caching, interrupt handling
• Security & Protection: authentication, authorization, access control
• Resource Allocation: fair and efficient distribution of all resources

OS AS RESOURCE MANAGER:
• CPU time → scheduler decides which process runs
• Memory → allocator assigns memory regions to processes
• I/O devices → device manager allocates printers, disks, network
• Files → file system manages storage space

OS AS ABSTRACTION LAYER:
• Hides interrupt handling, device registers, disk geometry
• Provides system calls as API for process to request OS services
• Makes hardware look simple and uniform to applications

SYSTEM SOFTWARE vs APPLICATION SOFTWARE:
• System software: OS, drivers, utilities — manages hardware, runs in background
• Application software: browsers, editors, games — runs on top of OS for user tasks

KERNEL:
• The CORE component of the OS, runs in privileged mode
• NOT the entire OS — OS = kernel + system programs + user interface
• Responsible for lowest-level operations: scheduling, memory mgmt, interrupts
• Monolithic kernel: all services in one address space (Linux, Unix)
• Microkernel: only essential services in kernel, rest in user space (Minix, QNX)

USER SPACE vs KERNEL SPACE:
• User space: where application code runs, restricted access to hardware
• Kernel space: where kernel runs, full access to hardware and all resources
• Transition happens through system calls (controlled, supervised entry)

MOST COMMON QUESTION:
"What is the difference between an OS and a kernel?"
Answer: Kernel is the core component that manages hardware resources. OS is the
entire package — kernel + system utilities + user interface. Every OS has a
kernel, but the kernel alone is not the complete OS.

FOLLOW-UP:
"Why do we need an OS at all?"
Answer: Without an OS, every program would need to handle hardware directly,
manage its own memory, handle interrupts, and coordinate with other programs.
This would be extremely inefficient, error-prone, and insecure. The OS
centralizes these tasks.

COMMON TRAP:
Saying "the kernel IS the OS" — this is WRONG. The kernel is a PART of the OS.
Also, saying the OS "controls hardware" is too vague — be specific: the OS
manages HARDWARE RESOURCES, not the hardware itself.

2. KERNEL + SYSTEM CALLS
================================================================================

CONCEPT:
The kernel is the core of the OS that manages hardware resources. System calls
are the interface between user applications and the kernel — they are the ONLY
way a process in user mode can request privileged operations.

SIMPLE EXPLANATION:
A system call is like a receptionist at a government office — you (the
application) can't walk into the back offices (kernel/hardware) yourself.
You make a request through the receptionist (system call), who handles it
on your behalf with proper authorization.

INTERVIEW ANSWER:
"System calls provide a controlled interface between user programs and the
kernel. When a program needs to do something privileged — like read a file,
create a process, or access the network — it makes a system call. This
triggers a mode switch from user mode to kernel mode, the kernel executes
the operation, and returns control back to the user program."

FLOW: Application → System Call Interface → Kernel → Hardware

CATEGORIES OF SYSTEM CALLS:
1. Process Control: fork(), exec(), exit(), wait(), terminate()
2. File Management: open(), read(), write(), close(), delete()
3. Device Management: ioctl(), read(), write() to device
4. Information Maintenance: getpid(), time(), alarm()
5. Communication: pipe(), shmget(), mmap(), socket()
6. Protection: chmod(), chown(), access()

USER MODE vs KERNEL MODE:
• User mode: limited instructions, no direct hardware access, restricted memory
• Kernel mode: full instruction set, direct hardware access, all memory accessible
• Mode bit in CPU register determines current mode
• Switch happens on: system call, interrupt, exception/error

PRIVILEGED OPERATIONS (require kernel mode):
• Direct I/O device access
• Memory management (page table modification)
• Interrupt handling
• Process scheduling
• Privileged instructions (halt, modify mode bit)

MOST COMMON QUESTION:
"What happens during a system call?"
Answer: (1) User program executes a special instruction (trap/syscall),
(2) CPU switches from user mode to kernel mode, (3) System call handler
identifies the requested service, (4) Kernel performs the operation,
(5) Result is returned, (6) CPU switches back to user mode, (7)
Execution resumes in user program.

FOLLOW-UP:
"What is the difference between a system call and a library function?"
Answer: A library function runs entirely in user mode. A system call
transfers control to kernel mode. For example, printf() is a library
function that internally calls write() system call.

COMMON TRAP:
Confusing system calls with library functions. NOT every function that
performs I/O is a system call — printf() is a library function; write()
is the actual system call. Also, system calls are SLOW compared to
regular function calls because of the mode switch overhead.

3. PROCESSES
================================================================================

CONCEPT:
A process is a program in execution. It is an active entity with resources
( memory, CPU state, open files ) while a program is a passive entity
(a file on disk). A process is the fundamental unit of work in an OS.

SIMPLE EXPLANATION:
A program is like a recipe (passive). A process is like actually cooking
the meal (active) — it uses ingredients (memory), utensils (CPU), and
the stove (I/O devices). Two people can cook two meals from the same
recipe — two processes can run the same program simultaneously.

INTERVIEW ANSWER:
"A process is a program in execution. It includes the program code, current
activity (program counter), stack, data section, and heap. The OS manages
processes through a Process Control Block, scheduling them on the CPU and
allocating them memory and resources."

PROCESS STATES:
New → Ready → Running → Waiting → Ready → Terminated
  │        │        │         │        │        │
  │        │        │         │        │        └─ Process finished
  │        │        │         │        └─────────── I/O completed / event occurred
  │        │        │         └─────────────────── Waiting for I/O or event
  │        │        └───────────────────────────── CPU allocated by scheduler
  │        └────────────────────────────────────── Admitted to ready queue
  └─────────────────────────────────────────────── Process being created

PCB (Process Control Block) CONTENTS:
• Process ID (PID)
• Process state (new, ready, running, waiting, terminated)
• Program counter (next instruction to execute)
• CPU registers (all register values at context switch)
• Scheduling info (priority, queue pointers, time quantum)
• Memory management info (page tables, base/limit registers)
• Accounting info (CPU time used, memory allocated)
• I/O status (list of I/O devices allocated, open files)

PROCESS CREATION:
• Parent process creates child processes
• Process hierarchy: tree structure
• Child can duplicate parent (fork) or load new program (exec)
• Resources: child may get subset of parent's resources or new ones
• Parent may wait for child to terminate (wait)

fork vs exec vs wait (CONCEPTUAL):
• fork: creates a COPY of the calling process (child is a clone)
• exec: replaces the current process image with a NEW program
• wait: parent pauses until a child process terminates

ZOMBIE PROCESS:
• Process has terminated but its PCB entry still exists
• Because parent hasn't yet called wait() to collect exit status
• Wastes a PCB slot in the process table
• Fixed by parent calling wait() or using signal handlers

ORPHAN PROCESS:
• Parent has terminated but child is still running
• Adopted by the init process (PID 1) or systemd
• init waits for them and reaps them properly

MOST COMMON QUESTION:
"What is the difference between a process and a thread?"
Answer: A process is an independent program in execution with its own
address space, resources, and control blocks. A thread is a single
sequence of execution within a process. Multiple threads within a
process share the same address space and resources but have their own
stack and registers.

FOLLOW-UP:
"What happens when a parent process is terminated before its child?"
Answer: The child becomes an orphan and is adopted by init/systemd,
which automatically reaps it when it terminates.

COMMON TRAP:
Thinking fork() creates a new program — it creates a COPY of the
existing process. exec() is what loads a new program. Also, thinking
zombie processes consume CPU — they only consume a PCB slot in memory.

4. THREADS
================================================================================

CONCEPT:
A thread is the smallest unit of execution within a process. It is a
"lightweight process" — a single thread of execution with its own program
counter, registers, and stack, but sharing the process's address space
and resources with other threads in the same process.

SIMPLE EXPLANATION:
Think of a process as a company and threads as employees. The company
has one office (address space), shared supplies (resources), and shared
goals (code/data). Each employee has their own desk (stack), their own
to-do list (program counter), and works on their own tasks independently.

INTERVIEW ANSWER:
"A thread is a basic unit of CPU execution within a process. While
processes are heavyweight — each with its own address space — threads
within a process share the same address space, code, and global data,
but each thread has its own stack, registers, and program counter.
This makes thread creation and context switching much faster than
process creation and switching."

PROCESS vs THREAD:
Feature              │ Process              │ Thread
─────────────────────┼──────────────────────┼──────────────────────
Address Space        │ Own (isolated)       │ Shared with siblings
Memory               │ Private              │ Shared (code, heap)
Creation Cost        │ High                 │ Low
Context Switch Cost  │ High                 │ Low
Communication        │ IPC (complex)        │ Shared memory (easy)
Failure Impact       │ Isolated             │ Can crash entire process
Resources            │ Own allocation       │ Shares process resources

THREADS SHARE:
• Code segment (same program instructions)
• Data segment (global variables)
• OS resources (open files, signals)
• Address space

THREADS DO NOT SHARE:
• Program counter
• Registers
• Stack (each thread has its own)
• Thread ID

USER-LEVEL THREADS vs KERNEL-LEVEL THREADS:
• User-level threads: managed by a thread library in user space
  - Kernel is unaware of them
  - Fast to create/switch (no kernel involvement)
  - Problem: if one thread blocks (I/O), entire process blocks
• Kernel-level threads: managed by the OS kernel
  - Kernel can schedule individual threads
  - If one thread blocks, others can continue
  - Slower creation/switch (kernel involvement needed)
• Many-to-one: many user threads → one kernel thread (one blocks, all block)
• One-to-one: one user thread → one kernel thread (best concurrency)
• Many-to-many: many user threads → many kernel threads (flexible)

MULTITHREADING BENEFITS:
• Responsiveness: UI stays responsive while background work happens
• Resource Sharing: threads share address space (cheaper than IPC)
• Economy: thread creation/switch is much cheaper than process
• Scalability: better utilization of multiprocessor systems

CONCURRENCY vs PARALLELISM:
• Concurrency: multiple tasks making progress in overlapping time periods
  (on single core: interleaving execution)
• Parallelism: multiple tasks executing simultaneously
  (on multi-core: true simultaneous execution)
• All parallel systems are concurrent, but not all concurrent systems
  are parallel

THREAD SAFETY:
• Code is thread-safe if it behaves correctly when accessed by multiple
  threads simultaneously
• Achieved through synchronization (mutexes, semaphores, atomic ops)
• Race conditions occur when thread safety is not maintained

MOST COMMON QUESTION:
"Why use threads instead of processes for concurrent tasks within the
same application?"
Answer: Threads share the same address space, so communication between
threads is simply reading/writing shared variables — no complex IPC
needed. Thread creation and context switching are also much cheaper.
Threads are ideal when tasks need to share data frequently.

FOLLOW-UP:
"What problem do user-level threads have with blocking I/O?"
Answer: If one user-level thread makes a blocking I/O call, the entire
process blocks because the kernel only sees one thread of execution.
Kernel-level threads don't have this problem — the OS can schedule
other threads of the same process while one is blocked.

COMMON TRAP:
Saying "threads have their own memory" — WRONG. Threads share the
process's memory. Each thread has its own STACK and REGISTERS only.
Also, confusing concurrency with parallelism on a single core.

5. CPU SCHEDULING
================================================================================

CONCEPT:
CPU scheduling is the process of deciding which process/thread gets the
CPU next when multiple are waiting. The scheduler selects from the ready
queue and allocates CPU time. The goal is to maximize CPU utilization,
throughput, and fairness while minimizing turnaround, waiting, and
response time.

SIMPLE EXPLANATION:
CPU scheduling is like a hospital triage nurse — patients (processes)
arrive constantly, and the nurse must decide who sees the doctor (CPU)
next based on urgency, wait time, and available resources.

INTERVIEW ANSWER:
"CPU scheduling determines which process runs when multiple are ready.
The short-term scheduler runs frequently and selects from the ready
queue. Different algorithms optimize for different criteria: FCFS is
simple but slow, SJF minimizes average waiting time but requires
prediction, Round Robin is fair with time quantum, and priority
scheduling handles importance but risks starvation."

SCHEDULER TYPES:
• Long-term (job scheduler): decides which processes enter ready queue
  - Controls degree of multiprogramming
  - Runs less frequently
• Short-term (CPU scheduler): decides which ready process gets CPU next
  - Runs very frequently (every few milliseconds)
  - Must be very fast
• Medium-term: swaps processes in/out of memory (swapping)

CPU BURST vs I/O BURST:
• CPU burst: process is doing computation, using CPU
• I/O burst: process is waiting for I/O, not using CPU
• Most processes alternate: CPU burst → I/O burst → CPU burst → ...
• Scheduling focuses on: when a CPU burst ends, which process gets CPU

SCHEDULING CRITERIA:
• CPU Utilization: keep CPU as busy as possible (target: 40-90%)
• Throughput: number of processes completed per unit time
• Turnaround Time: total time from submission to completion
  (includes waiting, executing, I/O)
• Waiting Time: total time spent waiting in the ready queue
• Response Time: time from submission to first response

PREEMPTIVE vs NON-PREEMPTIVE:
• Non-preemptive: process keeps CPU until it terminates or blocks for I/O
  - Simple, no race conditions on shared data
• Preemptive: OS can forcibly take CPU away from a process
  - Better responsiveness, but needs synchronization for shared data
  - Most modern OSes use preemptive scheduling

SCHEDULING ALGORITHMS:

FCFS (First-Come, First-Served):
• Simplest: processes served in arrival order
• Non-preemptive
• Problem: CONVOY EFFECT — short processes stuck behind long ones
  Example: 1 long process (24ms) + 3 short (1ms each)
  Average wait: (0 + 24 + 25 + 26)/4 = 18.75ms (terrible)

SJF (Shortest Job First):
• Process with smallest CPU burst goes first
• Optimal for AVERAGE WAITING TIME
• Non-preemptive version
• Problem: requires PREDICTING the next CPU burst length
  (use exponential averaging of past bursts)
• Starvation: long processes may never get CPU if short ones keep arriving

SRTF (Shortest Remaining Time First):
• Preemptive version of SJF
• If new process has shorter remaining time than current, preempt
• Still optimal but more complex, prediction still needed

PRIORITY SCHEDULING:
• Each process assigned a priority number
• Higher priority processes run first
• Problem: STARVATION — low priority processes may never run
• Solution: AGING — gradually increase priority of waiting processes
• Can be preemptive or non-preemptive

ROUND ROBIN (RR):
• Each process gets a TIME QUANTUM (q)
• After q expires, process goes to back of ready queue (preemptive)
• Fair — every process gets CPU time
• Time quantum TOO SMALL → too many context switches (overhead)
• Time quantum TOO LARGE → becomes FCFS (no time slicing benefit)
• Sweet spot: typically 10-100ms, should be large relative to
  context switch time but small relative to CPU burst

MULTILEVEL QUEUE:
• Ready queue split into multiple separate queues
• Each queue has its own scheduling algorithm
• Example: system processes, interactive processes, batch processes
• Fixed priority between queues (higher queue = higher priority)

MULTILEVEL FEEDBACK QUEUE:
• Like multilevel queue, but processes can MOVE between queues
• Process that uses too much CPU → demoted to lower priority queue
• Process that waits too long → promoted to higher priority queue
• Most flexible and commonly used in practice

STARVATION vs AGING:
• Starvation: process indefinitely waits because higher priority processes
  keep arriving or short processes keep getting CPU
• Aging: technique to prevent starvation by gradually increasing the
  priority of waiting processes

CONVOY EFFECT:
• Short processes stuck behind one long process in FCFS
• Average waiting time is very high
• Analogy: slow driver on a single-lane road blocking everyone

PRIORITY INVERSION:
• Lower priority process holds a resource needed by higher priority process
• Higher priority process waits while medium priority processes run
• Solution: priority inheritance — temporarily boost lower priority
  process's priority while it holds the resource

MOST COMMON QUESTION:
"Compare FCFS, SJF, RR, and Priority scheduling."
Answer: FCFS is simple but causes convoy effect. SJF minimizes average
waiting time but needs prediction and can starve long jobs. Round Robin
is fair and responsive — time quantum controls the tradeoff. Priority
scheduling handles importance but can starve low-priority processes
without aging.

FOLLOW-UP:
"Why is SJF optimal for average waiting time?"
Answer: By always running the shortest job first, we minimize the total
wait time across all processes. Mathematically, the sum of waiting times
is minimized when shorter jobs are completed earlier.

COMMON TRAP:
Saying "SJF is always better than FCFS" — SJF is better on average, but
FCFS can be better for specific cases (all similar length jobs). Also,
confusing response time with turnaround time — response time is time
to FIRST response, turnaround time is time to COMPLETION.

6. INTER-PROCESS COMMUNICATION (IPC)
================================================================================

CONCEPT:
IPC is the mechanism that allows processes to communicate and synchronize
with each other. Since processes have separate address spaces by default,
they need explicit mechanisms to share data and coordinate.

SIMPLE EXPLANATION:
IPC is like different departments in a company that need to share
information. They can't just walk into each other's offices (separate
address spaces), so they use memos (shared memory), email (message passing),
or phone calls (pipes/sockets).

INTERVIEW ANSWER:
"IPC mechanisms allow processes to communicate despite having separate
address spaces. The two main approaches are shared memory — where
processes access a common memory region, which is fast but requires
synchronization — and message passing — where processes send and
receive messages, which is simpler but has higher overhead. The choice
depends on the amount of data and synchronization requirements."

SHARED MEMORY:
• A region of memory is shared between two or more processes
• Fastest IPC method — processes read/write directly
• Problem: requires synchronization (race conditions possible)
• Examples: POSIX shared memory, System V shared memory
• Use case: large data transfer between processes on same machine

MESSAGE PASSING:
• Processes communicate by sending/receiving messages
• No shared memory to synchronize — OS handles it
• Higher overhead than shared memory (system calls, copying)
• Scales better for distributed systems
• Examples: sockets, pipes, message queues

PIPES:
• Unnamed pipe: communication between parent-child only, one-way
• Named pipe (FIFO): can communicate between unrelated processes
• Simple, but limited (byte stream, no message boundaries)

MESSAGE QUEUES:
• Kernel-maintained queue of messages
• Processes can send/receive messages of varying sizes
• Can have priorities for messages

SIGNALS:
• Asynchronous notification from one process to another
• Limited information (just the signal number)
• Examples: SIGKILL, SIGTERM, SIGUSR1

SOCKETS:
• General-purpose IPC, works across machines (network)
• Most flexible, but higher overhead
• Used for client-server communication

SHARED MEMORY vs MESSAGE PASSING:
Feature          │ Shared Memory       │ Message Passing
─────────────────┼─────────────────────┼─────────────────────
Speed            │ Very fast           │ Slower (OS involved)
Synchronization  │ Required manually   │ Handled by OS
Complexity       │ Harder (race cond.) │ Easier
Scalability      │ Same machine only   │ Works across machines

MOST COMMON QUESTION:
"When would you choose shared memory over message passing?"
Answer: When processes are on the same machine and need to exchange large
amounts of data frequently. Shared memory avoids copying overhead. Message
passing is better when simplicity, security, or cross-machine communication
is more important than raw speed.

FOLLOW-UP:
"Can shared memory be used across machines?"
Answer: No. Shared memory only works between processes on the same machine
because they share the same physical address space. For cross-machine
communication, use sockets or RPC.

COMMON TRAP:
Thinking IPC is only for inter-machine communication — IPC works between
processes on the SAME machine. For cross-machine, you need network
communication (sockets, RPC).

7. SYNCHRONIZATION
================================================================================

CONCEPT:
Synchronization is the coordination of concurrent processes or threads
to ensure correct execution when they access shared resources. Without
synchronization, race conditions lead to unpredictable and incorrect
results.

SIMPLE EXPLANATION:
Synchronization is like traffic lights at an intersection. Without them,
cars from different directions would collide (race condition). Traffic
lights ensure only one direction goes at a time (mutual exclusion) and
everyone takes turns fairly (progress + bounded waiting).

INTERVIEW ANSWER:
"Process synchronization ensures that concurrent processes accessing
shared resources produce correct results. The key problem is the race
condition — when the outcome depends on the unpredictable timing of
execution. We use mutual exclusion mechanisms like mutexes and
semaphores to ensure only one process accesses critical sections at
a time, preventing data corruption."

RACE CONDITION:
• Two or more processes access shared data simultaneously
• The final result depends on the timing/order of execution
• Example: Two threads incrementing a shared counter
  Both read value = 5, both compute 6, both write 6.
  Correct answer should be 7, but we get 6. (Lost update)
• Critical section: the code segment where shared resources are accessed

CRITICAL SECTION PROBLEM REQUIREMENTS:
1. Mutual Exclusion: at most ONE process in critical section at a time
2. Progress: if no process in CS, a waiting process must be able to enter
3. Bounded Waiting: no process waits indefinitely (prevents starvation)

MUTEX (Mutual Exclusion):
• Lock-based synchronization primitive
• lock(): acquire the lock (blocks if already held)
• unlock(): release the lock (allows waiting processes to proceed)
• Only ONE process can hold the mutex at a time
• Used to protect critical sections

SEMAPHORE:
• Integer variable accessed through two atomic operations: wait() and signal()
• Binary semaphore (0 or 1): equivalent to mutex
• Counting semaphore (0 to N): allows N concurrent accesses
• wait(S): if S > 0, decrement S and proceed; if S = 0, block
• signal(S): increment S and wake up a blocked process
• Used for more complex synchronization (producer-consumer, readers-writers)

MUTEX vs SEMAPHORE:
Feature         │ Mutex                   │ Semaphore
────────────────┼─────────────────────────┼─────────────────────────
Ownership       │ Only owner can unlock   │ Any process can signal
Purpose         │ Mutual exclusion        │ Signaling + mutual exclusion
Type            │ Lock                    │ Counter
Use case        │ Protect critical section │ Coordinate/access N resources

MONITOR:
• High-level synchronization construct (programming language feature)
• Combines shared data + procedures operating on it in one unit
• Only ONE process can be active inside a monitor at a time
• Uses condition variables: wait() and signal() (signal-and-wait semantics)
• Much easier to use correctly than semaphores
• Prevents errors like forgetting to unlock or signal

MONITOR vs SEMAPHORE:
Feature         │ Monitor                 │ Semaphore
────────────────┼─────────────────────────┼─────────────────────────
Abstraction     │ High-level (ADT)        │ Low-level
Encapsulation   │ Data + operations       │ Just a counter
Error-prone     │ Less (automatic)        │ More (manual unlock)
Language support │ Requires language       │ Any language
Correctness     │ Easier to prove         │ Harder

SIGNAL-AND-WAIT vs SIGNAL-AND-CONTINUE:
• Signal-and-wait: signaling process blocks, signaled process continues
  (used in Hoare monitors)
• Signal-and-continue: signaling process continues, signaled process
  waits until signaler leaves monitor (used in Mesa monitors)
• Most modern systems use signal-and-continue

MOST COMMON QUESTION:
"What is a race condition and how do you prevent it?"
Answer: A race condition occurs when two or more processes access shared
data concurrently and the outcome depends on execution order. It's
prevented using mutual exclusion — only one process can access the shared
resource at a time. This is achieved using mutexes, semaphores, or monitors.

FOLLOW-UP:
"Can you have a race condition with a semaphore?"
Answer: Yes, if the semaphore operations are not atomic, or if you have
a race condition in the code AROUND the critical section (e.g., two
processes accessing different shared variables without proper
synchronization).

COMMON TRAP:
Saying "semaphores prevent all race conditions" — they only prevent race
conditions on the critical section they protect. Race conditions can still
occur on OTHER shared data. Also, confusing mutex with semaphore — mutex
is for mutual exclusion; semaphore can also be used for signaling.

8. DEADLOCKS
================================================================================

CONCEPT:
A deadlock is a situation where two or more processes are each waiting
for a resource held by another, creating a circular chain of dependencies
that can never be resolved. All processes are stuck permanently.

SIMPLE EXPLANATION:
Two people in a narrow hallway, each trying to pass. Person A steps
right, Person B steps right. Both step left. Both step right. They're
stuck forever — each is waiting for the other to move, but neither
can move because the other is blocking the way.

INTERVIEW ANSWER:
"A deadlock occurs when processes are permanently blocked because each
holds a resource the other needs. It requires four conditions to exist
simultaneously: mutual exclusion, hold and wait, no preemption, and
circular wait. Since all four must be present, breaking any one of
them prevents deadlock."

FOUR COFFMAN CONDITIONS (MUST MEMORIZE):
1. Mutual Exclusion: resources cannot be shared — only one process at a time
2. Hold and Wait: processes hold resources while waiting for others
3. No Preemption: resources cannot be forcibly taken from processes
4. Circular Wait: circular chain of processes each waiting for the next's resource
ALL FOUR must be present for deadlock to occur.

DEADLOCK PREVENTION (break one condition):
• Break Mutual Exclusion: use sharable resources (not always possible)
• Break Hold and Wait: request all resources at once before execution
• Break No Preemption: if process can't get resource, release all held resources
• Break Circular Wait: enforce ordering on resource acquisition

DEADLOCK AVOIDANCE:
• Run-time check before granting resources
• Safe state: system can allocate resources to each process up to max
  and still complete all processes
• Unsafe state: may lead to deadlock
• Banker's Algorithm:
  - Process declares MAX resources it may need
  - Before granting, check if resulting state is safe
  - Only grant if safe
  - Data structures: Available, Maximum, Allocation, Need

BANKER'S ALGORITHM:
• Available: vector of available resources per type
• Max: matrix — max demand of each process
• Allocation: matrix — currently allocated to each process
• Need: matrix — remaining need (Max - Allocation)
• Safety Algorithm: check if a safe sequence exists
  (Can all processes eventually complete with available resources?)

DEADLOCK DETECTION:
• Allow deadlocks to occur, then detect and recover
• Wait-for graph: nodes = processes, edge = "waiting for"
  Circular cycle in wait-for graph = deadlock
• For single instance resources: wait-for graph
• For multiple instance resources: detection algorithm (similar to Banker's)

DEADLOCK RECOVERY:
• Process Termination: kill one or more deadlocked processes
  (abort all, or abort minimum number to break cycle)
• Resource Preemption: forcibly take resources from processes
  (need rollback and starvation prevention)

DEADLOCK vs STARVATION vs LIVELOCK:
• Deadlock: processes stuck forever waiting (no progress)
• Starvation: process waits indefinitely because others always get priority
  (there IS progress, just not for this process)
• Livelock: processes actively executing but making no progress
  (they keep responding to each other but neither makes progress)
  Like two people in a hallway constantly stepping aside for each other
  but always stepping the same way.

MOST COMMON QUESTION:
"What are the four necessary conditions for deadlock?"
Answer: (1) Mutual exclusion — resources can't be shared, (2) Hold and
wait — processes hold resources while requesting more, (3) No preemption
— resources can't be forcibly taken, (4) Circular wait — circular chain
of dependencies. All four must hold simultaneously.

FOLLOW-UP:
"What is the difference between deadlock prevention and avoidance?"
Answer: Prevention statically eliminates one of the four conditions (done
at design time, may reduce system utilization). Avoidance dynamically
checks each allocation at runtime using Banker's algorithm (more flexible
but requires advance knowledge of max resource needs).

COMMON TRAP:
Saying "deadlock only happens with two processes" — it can happen with
any number of processes in a circular wait. Also, confusing livelock with
deadlock — in livelock, processes ARE executing, but not making progress.


================================================================================
9. MEMORY MANAGEMENT
================================================================================

CONCEPT:
Memory management is the OS function responsible for allocating and
deallocating memory to processes, tracking what's in use, and providing
the abstraction of a large, private address space for each process
through virtual memory.

SIMPLE EXPLANATION:
Memory management is like apartment building management — each tenant
(process) gets their own apartment (address space) with a defined size.
The manager (OS) tracks which apartments are occupied, who's moving in
and out, and ensures no tenant can access another tenant's apartment.

INTERVIEW ANSWER:
"Memory management handles allocation and deallocation of memory to
processes, keeps track of available memory, and provides isolation
between processes. The OS uses techniques like paging and virtual
memory to give each process the illusion of a large, contiguous,
private address space, even when physical memory is limited and
fragmented."

LOGICAL ADDRESS vs PHYSICAL ADDRESS:
• Logical (virtual) address: address generated by CPU during execution
• Physical address: actual address in main memory (RAM)
• Logical address space: set of all logical addresses generated by program
• Physical address space: set of all physical addresses in memory
• MMU (Memory Management Unit): hardware that maps logical → physical
• User programs only see logical addresses, never physical addresses

ADDRESS BINDING:
The process of associating program instructions with memory addresses:
• Compile time: addresses fixed when program is compiled
  (if location changes, must recompile — inflexible)
• Load time: addresses determined when program is loaded into memory
  (must be loaded at same location every time)
• Execution time: addresses resolved during execution (most flexible)
  (allows process to be moved in memory — needs hardware support like MMU)

CONTIGUOUS ALLOCATION:
• Each process gets one contiguous block of memory
• Fixed partitioning: memory divided into fixed-size partitions
  - Simple but causes internal fragmentation (wasted space within partition)
• Variable partitioning: partitions created dynamically based on process size
  - No internal fragmentation, but causes external fragmentation
  - External fragmentation: free memory exists but is broken into small pieces
    that can't satisfy any request

ALLOCATION STRATEGIES:
• First Fit: allocate first hole that is big enough (fast, may waste space)
• Best Fit: allocate smallest hole that is big enough (minimizes leftover,
  but slow to search, creates tiny unusable fragments)
• Worst Fit: allocate largest hole (leaves largest leftover, but also slow)
• Next Fit: like first fit but starts searching from last allocation point

INTERNAL vs EXTERNAL FRAGMENTATION:
• Internal: allocated memory is larger than needed, space wasted inside
  (occurs with fixed partitioning)
• External: free memory exists but is not contiguous enough to satisfy
  a request (occurs with variable partitioning / contiguous allocation)
• Solution to external fragmentation: PAGING (divide memory into small
  fixed-size blocks that don't need to be contiguous)

MOST COMMON QUESTION:
"What is the difference between internal and external fragmentation?"
Answer: Internal fragmentation is wasted space INSIDE an allocated region
(allocated block is bigger than needed). External fragmentation is free
memory that exists but is broken into non-contiguous pieces too small to
use. Internal happens with fixed-size allocation; external with variable.

FOLLOW-UP:
"How does paging solve external fragmentation?"
Answer: Paging divides both physical memory and process address space
into fixed-size blocks (pages/frames). A process's pages can be placed
in ANY available frames, no contiguity needed. Since any free frame can
be used for any page, external fragmentation is eliminated.

COMMON TRAP:
Saying "paging eliminates all fragmentation" — paging eliminates
EXTERNAL fragmentation but can still cause INTERNAL fragmentation
(last page of process may not fully fill a frame). Also, thinking
logical and physical addresses are always the same — they're only
the same if no address relocation (no virtual memory).


================================================================================
10. PAGING
================================================================================

CONCEPT:
Paging is a memory management scheme that eliminates external fragmentation
by dividing physical memory into fixed-size frames and logical memory
into fixed-size pages. A page table maps each page to a frame, allowing
non-contiguous allocation.

SIMPLE EXPLANATION:
Paging is like a book's index — instead of reading the entire book to
find a topic (contiguous search), you look up the page number in the
index (page table) and go directly to the right page (frame). Pages
can be in any order on the shelf (frames in memory), but the index
tells you exactly where each one is.

INTERVIEW ANSWER:
"Paging divides memory into fixed-size blocks: pages (logical) and
frames (physical). A page table maps each process's page to a memory
frame. This allows a process's pages to be scattered across physical
memory, eliminating external fragmentation. Address translation uses
the page number to look up the frame, then adds the offset."

KEY TERMS:
• Page: fixed-size block of logical memory (process's address space)
• Frame: fixed-size block of physical memory (RAM)
• Page table: per-process data structure mapping page → frame
• Offset: position within the page/frame
• Page number: index into the page table

ADDRESS TRANSLATION:
Logical address = [Page Number | Offset]
Steps: (1) Extract page number from logical address
       (2) Look up frame number in page table using page number
       (3) Physical address = [Frame Number | Offset]
       (4) Combine frame number with offset to get physical address

PAGE TABLE ENTRY CONTAINS:
• Frame number (where the page is in physical memory)
• Valid/Invalid bit (is this page currently in memory?)
• Reference bit (has this page been accessed recently?)
• Modified/dirty bit (has this page been written to?)
• Protection bits (read, write, execute permissions)

PAGE TABLE FEATURES:
• One page table per process
• Stored in main memory (can be large)
• Page table base register (PTBR) points to current process's page table
• Page table length register (PTLR) stores size of page table

PROBLEMS WITH SIMPLE PAGING:
• Page table can be very large (e.g., 32-bit address, 4KB pages → 1M entries)
• Accessing page table requires extra memory reference (doubles access time)
• Solutions: TLB (translation lookaside buffer), multi-level page tables,
  hashed page tables

MULTI-LEVEL PAGE TABLES:
• Divide page table into smaller parts
• Only load parts that are needed
• Reduces memory for page tables (most entries unused for sparse address spaces)

MOST COMMON QUESTION:
"How does address translation work in paging?"
Answer: The logical address is split into page number and offset. The page
number is used as an index into the page table to find the frame number.
The frame number is combined with the offset to form the physical address.
This translation is done by the MMU, often accelerated by a TLB.

FOLLOW-UP:
"What is the overhead of paging?"
Answer: Each memory access requires two accesses: one for the page table
and one for the actual data. This effectively doubles memory access time.
The TLB (hardware cache for page table) mitigates this — a TLB hit gives
the translation in one access.

COMMON TRAP:
Confusing pages with frames — pages are logical (process view), frames
are physical (memory view). Also, thinking page tables are stored in
registers — they're in main memory, with only the base address (PTBR)
in a register.


================================================================================
11. SEGMENTATION
================================================================================

CONCEPT:
Segmentation is a memory management scheme that divides a process's
address space into variable-sized segments based on logical divisions
(code, data, stack). Each segment has a name and a length, and is
mapped to physical memory through a segment table.

SIMPLE EXPLANATION:
Segmentation is like organizing a filing cabinet by function — one
drawer for code (labeled "CODE"), one for data (labeled "DATA"),
one for stack (labeled "STACK"). Each drawer is a different size
depending on its contents. The segment table is like a card catalog
telling you where each drawer is located.

INTERVIEW ANSWER:
"Segmentation divides a process's address space into variable-sized
logical units called segments — typically code, data, and stack. A
segment table stores the base address and length of each segment.
Unlike paging, segments correspond to logical program divisions,
making them meaningful to the programmer and the OS."

SEGMENT TABLE ENTRY:
• Segment base: starting physical address of the segment
• Segment length (limit): size of the segment
• Protection bits (read, write, execute)

SEGMENTED ADDRESS:
Logical address = [Segment Number | Offset]
Steps: (1) Look up segment number in segment table
       (2) Check if offset < segment length (otherwise trap: segmentation fault)
       (3) Physical address = segment base + offset

PAGING vs SEGMENTATION:
Feature         │ Paging                    │ Segmentation
────────────────┼───────────────────────────┼───────────────────────────
Division        │ Fixed-size pages          │ Variable-size segments
External Frag.  │ None                      │ Yes
Internal Frag.  │ Possible (last page)      │ No
User Visibility │ Invisible to user         │ Visible (logical units)
Page/Seg Table  │ Page number → frame       │ Base + length
Use case        │ Memory management         │ Logical organization, protection

SEGMENTATION FAULT:
• When offset exceeds segment length (accessing beyond segment boundary)
• Hardware detects this and generates an exception
• This is the "segmentation fault" error programmers encounter

MOST COMMON QUESTION:
"What is the difference between paging and segmentation?"
Answer: Paging divides memory into fixed-size blocks (invisible to user),
eliminates external fragmentation. Segmentation divides into variable-size
logical units (visible to user), causes external fragmentation but is
more natural for program organization. Many modern systems combine both
(segmented paging).

FOLLOW-UP:
"Why does segmentation cause external fragmentation but paging doesn't?"
Answer: Paging uses fixed-size frames, so any free frame can hold any
page. Segmentation uses variable-size segments, so free memory can be
broken into non-contiguous pieces too small to fit any segment.

COMMON TRAP:
Saying "segmentation is obsolete" — it's still used in x86 architecture
(real mode uses segmentation, protected mode combines segmentation with
paging). Also, confusing segmentation fault (access violation) with
segmentation (memory management technique).


================================================================================
12. VIRTUAL MEMORY
================================================================================

CONCEPT:
Virtual memory is a memory management technique that creates the
abstraction of a very large address space for each process, larger
than the actual physical memory available. Only the currently needed
parts of a process are kept in physical memory.

SIMPLE EXPLANATION:
Virtual memory is like a library card system — you don't need all books
on your desk (physical memory). You only pull the book you're currently
reading. The card catalog (page table) tells you where each book is
stored in the library (disk). When you need a new book, you fetch it
from the library and put it on your desk.

INTERVIEW ANSWER:
"Virtual memory decouples logical address space from physical memory,
allowing processes to use addresses beyond actual RAM size. Only
currently needed pages are in physical memory; the rest reside on
disk. When a needed page isn't in memory, a page fault occurs and
the OS loads it from disk. This enables running programs larger than
physical memory and improves multiprogramming."

WHY VIRTUAL MEMORY:
• Run programs larger than physical memory
• More processes in memory (higher multiprogramming → better CPU utilization)
• Isolation between processes (each has its own virtual address space)
• Shared pages between processes (code sharing)

DEMAND PAGING:
• Pages loaded into memory only when needed (on demand)
• Initially, all pages marked as "not in memory" in page table
• When a page is accessed → page fault → OS loads it from disk
• Lazy approach — don't load what you might not need

PAGE FLOW (critical to understand):
1. CPU references a virtual address
2. MMU checks page table → page NOT in memory (valid bit = 0)
3. PAGE FAULT trap to OS
4. OS finds the page on disk (swap space)
5. OS finds a free frame in memory
6. OS schedules disk operation to load the page into the frame
7. Process is BLOCKED (waiting for I/O)
8. Disk I/O completes → interrupt to OS
9. OS updates page table (set valid bit, update frame number)
10. OS unblocks the process (moves to ready queue)
11. Process resumes — instruction restarts and succeeds

PAGE FAULT COST:
• Page fault requires disk access (milliseconds)
• Regular memory access requires nanoseconds
• Page faults are VERY expensive — 100,000x slower than memory access
• Goal: minimize page fault rate (most programs have good locality)

LOCALITY OF REFERENCE:
• Temporal locality: recently accessed addresses likely to be accessed again
• Spatial locality: addresses near recently accessed ones likely to be accessed
• Programs tend to access a small working set of pages frequently
• This makes virtual memory practical — only a few pages needed at a time

SWAP SPACE:
• Dedicated disk area for pages not in physical memory
• When a page is evicted from memory, it goes to swap space
• When needed again, loaded back from swap space

MOST COMMON QUESTION:
"What happens during a page fault?"
Answer: The CPU accesses a page not in memory. A page fault trap occurs.
The OS locates the needed page on disk, finds a free frame, loads the page
from disk to the frame (process blocked during disk I/O), updates the
page table, and restarts the instruction that caused the fault.

FOLLOW-UP:
"How does virtual memory affect performance?"
Answer: With good locality, most accesses hit pages already in memory
(fast). Page faults are expensive but infrequent. Virtual memory enables
higher multiprogramming (more processes in memory), improving overall
throughput despite per-process overhead.

COMMON TRAP:
Thinking virtual memory means "more memory" — it gives the ILLUSION of
more memory by using disk as overflow. It doesn't make disk as fast as
RAM. Also, thinking page faults are normal — they ARE expected, but
high page fault rates indicate thrashing or insufficient memory.


================================================================================
13. PAGE REPLACEMENT
================================================================================

CONCEPT:
When all frames are full and a new page must be loaded, the OS must
choose a victim page to evict. Page replacement algorithms determine
which page to remove, aiming to minimize future page faults.

SIMPLE EXPLANATION:
Page replacement is like deciding which book to return to the library
when your desk is full and you need space for a new book. You'd want
to return the book you're LEAST likely to need again soon. Different
algorithms use different strategies to make this decision.

INTERVIEW ANSWER:
"When a page fault occurs and no free frames exist, the OS must replace
an existing page. FIFO is simplest but can suffer from Belady's anomaly.
LRU approximates optimal replacement by evicting least recently used
pages. The clock algorithm is a practical approximation of LRU that's
efficient to implement. Optimal replacement minimizes faults but is
theoretically unimplementable."

REPLACEMENT ALGORITHMS:

FIFO (First-In, First-Out):
• Replace the oldest page in memory
• Simple to implement (queue)
• NOT optimal — Belady's anomaly possible
• Belady's anomaly: increasing frames can INCREASE page faults
  (only FIFO has this anomaly)

OPTIMAL (MIN):
• Replace the page that will not be used for the longest time in the future
• THEORETICAL BEST — produces minimum page faults
• NOT IMPLEMENTABLE — requires future knowledge
• Used as a benchmark to evaluate other algorithms

LRU (Least Recently Used):
• Replace the page that has not been used for the longest time
• Good practical approximation of Optimal
• Based on past behavior (temporal locality)
• Expensive to implement perfectly:
  - Need to timestamp every memory access
  - Or maintain a stack of page references
• Hardware support needed (counter or stack per page)

CLOCK / SECOND CHANCE:
• Approximates LRU efficiently
• Pages arranged in circular buffer with reference bit
• Clock hand scans pages:
  - If reference bit = 0: replace this page
  - If reference bit = 1: set bit to 0, move to next page
• Gives "second chance" to recently used pages
• Much cheaper than perfect LRU
• Most commonly used in practice

BELADY'S ANOMALY:
• FIFO can have MORE page faults with MORE frames
• Example: reference string 1,2,3,4,1,2,5,1,2,3,4,5
  - 3 frames: 9 page faults
  - 4 frames: 10 page faults (!!!)
• LRU and Optimal do NOT have this anomaly
• Only FIFO suffers from Belady's anomaly

COMPARISON:
Algorithm   │ Optimality │ Implementation Cost │ Belady's Anomaly
────────────┼────────────┼─────────────────────┼─────────────────
FIFO        │ Poor       │ Very low            │ YES
Optimal     │ Best       │ Impossible          │ No
LRU         │ Very good  │ High (hardware)     │ No
Clock       │ Good       │ Low                 │ No

MOST COMMON QUESTION:
"Compare FIFO and LRU page replacement."
Answer: FIFO is simple but can produce poor results and suffers from
Belady's anomaly. LRU is much better because it leverages temporal
locality — recently used pages are likely to be used again. However,
LRU is expensive to implement perfectly; the clock algorithm is a
practical approximation.

FOLLOW-UP:
"What is Belady's anomaly?"
Answer: It's a phenomenon where increasing the number of page frames
leads to MORE page faults, not fewer. This is counterintuitive and
only occurs with FIFO replacement. LRU and optimal algorithms don't
suffer from this anomaly.

COMMON TRAP:
Saying "more frames always means fewer page faults" — this is true
for LRU and Optimal, but NOT for FIFO (Belady's anomaly). Also,
confusing LRU with LFU (Least Frequently Used) — LRU tracks recency,
LFU tracks frequency.


================================================================================
14. TLB (Translation Lookaside Buffer)
================================================================================

CONCEPT:
The TLB is a small, fast hardware cache that stores recent page table
entries. It accelerates virtual-to-physical address translation by
avoiding the need to access the page table in main memory for every
memory reference.

SIMPLE EXPLANATION:
TLB is like a sticky note on your monitor with the most-used phone
numbers. Instead of looking up the phone book (page table in memory)
every time you call, you check the sticky note (TLB) first. If the
number is there (TLB hit), you save time. If not (TLB miss), you
check the phone book.

INTERVIEW ANSWER:
"The TLB is a hardware cache for page table entries that dramatically
speeds up address translation. On a TLB hit, the frame number is
obtained in a single cycle without accessing main memory. On a TLB
miss, the page table must be consulted, which is slower. Since
programs exhibit locality, most accesses are TLB hits, making the
average translation time very fast."

TLB OPERATION:
1. CPU generates logical address (page number + offset)
2. TLB is searched for page number
3. TLB HIT: frame number found → combine with offset → physical address
4. TLB MISS: page not in TLB → look up page table in memory
   - Load page table entry into TLB
   - Retry the instruction → TLB hit
5. TLB entry contains: page number, frame number, valid bit, protection bits

TLB PERFORMANCE:
• TLB is very small (64-1024 entries typically)
• Fast (1 cycle access, like L1 cache)
• If TLB hit rate = 99%, effective access time ≈ 1.01 × memory access time
• Without TLB: every memory access requires 2 accesses (page table + data)
• TLB makes paging overhead negligible in most cases

TLB FLUSH:
• When context switch occurs, TLB entries may be invalid
• Old process's entries don't apply to new process
• TLB must be flushed (cleared) on context switch
• Some TLBs have ASID (Address Space ID) to avoid full flush

MULTI-LEVEL TLB:
• L1 TLB: smallest, fastest, few entries
• L2 TLB: larger, slower, more entries
• Similar to L1/L2 data cache hierarchy

MOST COMMON QUESTION:
"What is the purpose of a TLB?"
Answer: The TLB caches page table entries to speed up address translation.
Without a TLB, every memory access would require an extra memory access
to read the page table. The TLB provides near-instant lookups, reducing
the effective memory access time close to a single access.

FOLLOW-UP:
"What happens on a TLB miss?"
Answer: The hardware (or OS) walks the page table in memory to find the
mapping, loads it into the TLB, and retries the address translation.
If the page isn't in memory at all, a page fault occurs instead.

COMMON TRAP:
Saying "TLB stores pages" — TLB stores PAGE TABLE ENTRIES (mappings),
not pages themselves. Also, thinking TLB miss = page fault — TLB miss
means the mapping isn't cached (but the page is still in memory).
Page fault means the page isn't in memory at all.


================================================================================
15. FILE SYSTEMS
================================================================================

CONCEPT:
A file system organizes data on storage devices into files and
directories. It provides a logical view of storage, manages metadata,
enforces access control, and provides efficient storage and retrieval.

SIMPLE EXPLANATION:
A file system is like a library's organization system — books (files)
are organized into sections (directories), each book has a catalog
entry (metadata), and there's a librarian (file system) who helps
you find, add, or remove books efficiently.

INTERVIEW ANSWER:
"A file system provides a structured way to store and retrieve data
on disk. It organizes data into files, groups files into directories,
and maintains metadata like file size, permissions, and timestamps.
It manages disk space allocation, provides access control, and offers
operations like create, read, write, delete, and rename."

FILE ATTRIBUTES:
• Name: human-readable identifier
• Identifier: unique tag (inode number) for the file system
• Type: regular file, directory, symbolic link
• Size: current size in bytes
• Location: pointer to location on disk
• Protection: read/write/execute permissions
• Timestamps: creation, last access, last modification

FILE OPERATIONS:
• Create, Delete
• Open, Close
• Read, Write
• Append, Seek
• Rename, Truncate

DIRECTORY STRUCTURE:
• Single-level: all files in one directory (flat — simple, unscalable)
• Two-level: user directories + files within (limited organization)
• Tree: hierarchical directories (most common — Unix, Windows)
• Acyclic graph: directories can share subdirectories (hard/soft links)
• General graph: allows cycles (complex, requires garbage collection)

FILE ALLOCATION METHODS:
• Contiguous: file stored in consecutive blocks
  + Fast sequential and direct access
  - External fragmentation, size must be known at creation
• Linked: each block points to next block
  + No external fragmentation, no size limit
  - Slow random access (must traverse links), pointer overhead
• Indexed: index block contains pointers to all file blocks
  + Fast random access, no external fragmentation
  - Index block overhead, pointer management

FILE SYSTEM EXAMPLES:
• FAT32: simple, used in USB drives, 4GB file size limit
• NTFS: Windows, supports permissions, encryption, journaling
• ext4: Linux, journaling, supports large files
• APFS: Apple, optimized for SSDs, snapshots, cloning

INODE (Unix/Linux):
• Data structure storing file metadata (not the file name)
• Contains: permissions, owner, size, timestamps, pointers to data blocks
• Directory entry: maps file name → inode number
• Enables fast file lookup

MOST COMMON QUESTION:
"Compare contiguous, linked, and indexed file allocation."
Answer: Contiguous is fastest for sequential access but causes external
fragmentation. Linked eliminates fragmentation but has slow random access.
Indexed provides fast random access without fragmentation but requires
extra space for index blocks. Most modern systems use indexed allocation.

FOLLOW-UP:
"What is an inode?"
Answer: An inode is a data structure in Unix/Linux file systems that
stores all metadata about a file except its name. It contains
permissions, ownership, size, timestamps, and pointers to data blocks.
Directory entries map filenames to inode numbers.

COMMON TRAP:
Thinking file names are stored in inodes — they're stored in directory
entries. Also, confusing file allocation with memory allocation —
they solve similar problems (fragmentation) but at different scales.


================================================================================
16. I/O + INTERRUPTS + DMA
================================================================================

CONCEPT:
I/O management handles communication between the CPU and peripheral
devices (disk, keyboard, network, display). The OS uses interrupts and
DMA to efficiently manage I/O without wasting CPU cycles.

SIMPLE EXPLANATION:
I/O management is like a receptionist handling multiple phone lines.
Instead of holding each call (busy waiting), the receptionist takes
notes (DMA transfers data) and gets notified when a call comes in
(interrupt). The CPU doesn't waste time checking if anything happened
— it gets interrupted only when something actually happens.

INTERVIEW ANSWER:
"I/O management coordinates data transfer between CPU and devices.
Polling wastes CPU cycles checking device status. Interrupts are more
efficient — the device notifies the CPU when it's ready. DMA takes
this further by letting a dedicated controller transfer large blocks
of data directly between device and memory without CPU involvement,
freeing the CPU for other work."

I/O SUBSYSTEM:
• Device controllers: hardware that manages a specific device
  (each controller has its own registers and buffer)
• Device drivers: OS software that knows how to talk to specific controllers
• I/O kernel subsystem: buffering, caching, spooling, device allocation

I/O METHODS:

POLLING (Programmed I/O):
• CPU repeatedly checks (busy-waits) if device is ready
• Simple but WASTES CPU cycles (busy waiting)
• Like standing at the door waiting for someone — can't do anything else
• Only suitable for very fast devices

INTERRUPTS:
• Device signals CPU when it needs attention (no busy waiting)
• CPU can do other work, then respond when interrupted
• Interrupt controller signals CPU → CPU saves current state →
  executes interrupt handler → restores state → resumes
• Much more efficient than polling
• Two types:
  - Hardware interrupts: from devices (disk I/O complete, key press)
  - Software interrupts/traps: from programs (system call, page fault,
    division by zero)

INTERRUPT HANDLING FLOW:
1. Device raises interrupt signal
2. CPU finishes current instruction
3. CPU saves current process state (PCB)
4. CPU looks up interrupt vector table
5. CPU jumps to appropriate interrupt handler (ISR)
6. ISR processes the interrupt (reads data, acknowledges device)
7. ISR restores saved state
8. CPU resumes the interrupted process

DMA (Direct Memory Access):
• Hardware controller that transfers data between device and memory
  WITHOUT CPU involvement
• CPU sets up DMA: tells it source, destination, and amount of data
• DMA controller handles the entire transfer
• DMA signals CPU when transfer is complete (interrupt)
• Ideal for LARGE data transfers (disk reads, network packets)
• CPU free to do other work during transfer

POLLING vs INTERRUPTS vs DMA:
Feature    │ Polling          │ Interrupts       │ DMA
───────────┼──────────────────┼──────────────────┼─────────────────
CPU Usage  │ 100% (busy wait) │ Minimal          │ Minimal
Efficiency │ Very low         │ High             │ Very high
Complexity │ Simple           │ Moderate         │ Complex
Use Case   │ Fast devices     │ General I/O      │ Large data transfers

MOST COMMON QUESTION:
"What is the difference between polling and interrupts?"
Answer: Polling requires the CPU to repeatedly check device status,
wasting cycles. Interrupts allow the device to notify the CPU when
ready, so the CPU can do other work. Interrupts are much more
efficient and are the standard approach in modern systems.

FOLLOW-UP:
"How does DMA improve I/O performance?"
Answer: DMA transfers data directly between device and memory without
CPU involvement. The CPU only sets up the transfer and gets interrupted
when complete. This frees the CPU to execute other processes during
large data transfers, dramatically improving system throughput.

COMMON TRAP:
Saying "interrupts are always better than polling" — for very high-speed
devices where interrupts would flood the CPU, polling can actually be
more efficient. Also, confusing DMA with interrupts — they're different
mechanisms that work together (DMA handles transfer, interrupt signals
completion).


================================================================================
17. SECURITY / PROTECTION
================================================================================

CONCEPT:
Security protects the system from unauthorized access and threats.
Protection is a mechanism for controlling access to resources. Together,
they ensure that processes can only access what they're authorized to.

SIMPLE EXPLANATION:
Protection is like locks on doors — each room (resource) has a lock,
and only people with the right key (permission) can enter. Security
is the entire security system — locks, cameras, guards, and policies
that keep the building safe.

INTERVIEW ANSWER:
"Security and protection ensure system integrity and data confidentiality.
Protection mechanisms control how processes access resources — through
access control lists, permissions, and privilege levels. Security goes
beyond protection to include authentication, authorization, encryption,
and defense against threats. The OS enforces these through hardware
support like user/kernel mode and memory protection."

AUTHENTICATION vs AUTHORIZATION:
• Authentication: VERIFYING identity ("Who are you?")
  - Passwords, biometrics, tokens, certificates
• Authorization: GRANTING permissions ("What can you do?")
  - Based on identity, role, or attributes
  - Access control lists (ACLs), capabilities
• Must authenticate BEFORE authorizing

ACCESS CONTROL:
• Discretionary (DAC): owner decides who has access (Unix file permissions)
• Mandatory (MAC): system enforces policies (SELinux, military systems)
• Role-based (RBAC): access based on user role (admin, user, guest)
• Access control matrix: subject × resource → permissions
• Access control list: per-resource list of allowed subjects
• Capabilities: per-subject list of allowed resources

USER MODE vs KERNEL MODE (Security Perspective):
• User mode: limited access, cannot execute privileged instructions
  - Prevents processes from accessing other processes' memory
  - Prevents direct hardware access
• Kernel mode: full access, can execute all instructions
  - Only OS kernel runs in kernel mode
  - System calls are the controlled entry point

ISOLATION:
• Each process has its own virtual address space (cannot access others)
• Enforced by MMU and page table permissions
• Critical for security — prevents malicious/erroneous processes
  from corrupting others

LEAST PRIVILEGE:
• Processes should have ONLY the minimum permissions needed to function
• Reduces damage from bugs or attacks
• Example: web server runs as non-root, not as administrator

PROTECTION vs SECURITY:
• Protection: mechanism to control access to internal OS objects
  (memory, CPU, I/O devices)
  - Enforced by hardware and OS
  - Prevents processes from interfering with each other
• Security: overall system defense against external and internal threats
  - Authentication, authorization, encryption, auditing
  - Broader scope including physical security

COMMON SECURITY MECHANISMS:
• ASLR (Address Space Layout Randomization): randomize memory layout
  to prevent buffer overflow attacks
• DEP/NX bit: mark data pages non-executable
• Sandboxing: restrict process capabilities
• Virtualization: isolate environments
• Encryption: protect data at rest and in transit

MOST COMMON QUESTION:
"What is the difference between authentication and authorization?"
Answer: Authentication verifies identity (password, biometrics).
Authorization determines what an authenticated user can do (permissions,
access control). You authenticate first, then authorization controls
what resources you can access based on your identity and role.

FOLLOW-UP:
"Why is user/kernel mode important for security?"
Answer: User mode prevents processes from directly accessing hardware
or other processes' memory. All privileged operations must go through
system calls, which are validated by the kernel. This boundary
prevents processes from bypassing security checks.

COMMON TRAP:
Confusing protection with security — protection is internal (process
isolation, access control), security is broader (threats, attacks,
authentication). Also, thinking user mode is sufficient for security —
you still need authentication, authorization, and encryption for
complete security.

18. PERFORMANCE
================================================================================

CONCEPT:
OS performance is measured by how efficiently the system uses resources
and responds to user requests. Key metrics include CPU utilization,
throughput, latency, and response time. The OS must balance competing
performance goals through scheduling, caching, and resource management.

SIMPLE EXPLANATION:
OS performance is like restaurant efficiency — you want the kitchen
(CPU) busy but not overwhelmed, orders (processes) completed quickly,
customers (users) served promptly, and no one waiting too long.
The OS is the restaurant manager optimizing all these simultaneously.

INTERVIEW ANSWER:
"OS performance is measured across several dimensions: CPU utilization
(how busy the CPU is), throughput (processes completed per unit time),
turnaround time (total time for a process), waiting time (time spent
in ready queue), and response time (time to first response). The OS
optimizes these through scheduling algorithms, memory management,
caching, and I/O management, often making tradeoffs between them."

KEY PERFORMANCE METRICS:
• CPU Utilization: percentage of time CPU is busy (target: 40-90%)
  - Too low: resources wasted
  - Too high: system overloaded, long queues
• Throughput: number of processes completed per time unit
  - Higher = better (more work done)
• Turnaround Time: submission → completion (includes everything)
  - Average turnaround time should be minimized
• Waiting Time: time in ready queue (not including execution or I/O)
  - Average waiting time should be minimized
• Response Time: submission → first response
  - Critical for interactive systems

CONTEXT SWITCHING OVERHEAD:
• Saving and restoring process state (PCB)
• Involves multiple memory accesses and CPU cycles
• Typical: 1-10 microseconds
• Frequent context switching degrades performance significantly
  - Too-small time quantum in RR → excessive switching
  - Too many threads/processes → more switching

CACHE HIERARCHY:
• L1 cache: smallest, fastest, closest to CPU (1-4 cycles)
• L2 cache: larger, slower (10-20 cycles)
• L3 cache: shared among cores (30-50 cycles)
• Main memory (RAM): 100-300 cycles
• Disk: 10,000,000+ cycles
• Cache hit: data found in cache (fast)
• Cache miss: data not in cache, must go to slower memory

MEMORY ACCESS PERFORMANCE:
• Locality of reference is key to good performance
  - Temporal: recently accessed → likely to be accessed again
  - Spatial: nearby addresses → likely to be accessed next
• Virtual memory with TLB provides fast address translation
• Page faults are expensive → minimize with good replacement algorithms

I/O BOTTLENECKS:
• Disk I/O is often the biggest bottleneck (orders of magnitude slower
  than CPU/memory operations)
• Solutions: buffering, caching, spooling, DMA, read-ahead
• SSD vs HDD: SSDs much faster but still slower than RAM

COMMON TRADEOFFS:
• Throughput vs Latency: batch processing improves throughput but
  increases individual latency
• Fairness vs Efficiency: giving everyone equal time (RR) vs letting
  short jobs finish fast (SJF)
• Memory vs Speed: more caching = faster access but more memory used
• Multiprogramming vs Overhead: more processes = better utilization
  but more context switching
• Preemption vs Overhead: more frequent preemption = better response
  but more switching overhead

MOST COMMON QUESTION:
"What are the key performance metrics for an OS?"
Answer: CPU utilization (how busy the CPU is), throughput (processes
completed per unit time), turnaround time (total time for a process),
waiting time (time in ready queue), and response time (time to first
response). Different workloads prioritize different metrics.

FOLLOW-UP:
"Why is context switching expensive?"
Answer: Context switching requires saving the entire state of the
current process (all registers, program counter, memory mappings)
and loading the state of the next process. This involves multiple
memory accesses, TLB flushes, and pipeline flushes, all of which
take CPU cycles without doing useful work.

COMMON TRAP:
Saying "higher CPU utilization is always better" — utilization above
90% often means the system is overloaded with long queues. Optimal
utilization depends on the workload. Also, confusing throughput with
latency — you can have high throughput (many jobs completed) but
high latency (each job takes long).
